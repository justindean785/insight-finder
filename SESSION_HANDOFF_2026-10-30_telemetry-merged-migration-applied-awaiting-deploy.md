## 5. Traps found this session

- **`npm run lint` lints `supabase/functions/` too.** Run every step of the CI job (`lint`, `typecheck`, `test:coverage`, `build`) plus the edge suite, in CI's order, before pushing. A local lint count includes gitignored `coverage/` artifacts left by `test:coverage` (3 extra warnings); CI lints before coverage exists. Use `--ignore-pattern 'coverage/**'` to compare.
- **Any `deno` run can rewrite `deno.lock`** — `git checkout -- deno.lock` before committing; pass `--no-lock`.
- **Codex reviews when a draft is marked ready** (~1.5 min; findings land as review threads). **Graphify** posts ~1–9 min later (advisory coupling notes; gate PASS). **Wait for both before merging an edge PR.** After a merge the PR subscription ends, so a late review comment will not wake you — read it explicitly.
- **PostgREST rejects an insert that names an unknown column**, which drops the whole parent row and every child row (one `console.warn`). Schema first, always; the kill switch is the rollback.
- Postgres will not run as root, and the scratchpad is not readable by the `postgres` user — a throwaway cluster for validating migrations needs its own directory (e.g. under `/var/tmp`), removed afterwards.
- `mcp__Lovable__query_database` executes DDL as well as SELECT; production DDL needs JD's explicit go. Read-only metadata queries on `tool_usage_log` / `orchestrator_*` (counts, durations, tool names — never `input_json`) were used freely for measurement.
- Cross-check worth knowing: the Activity tab of JD's `pattyspartyrental` case showed `minimax_correlate` 59 s (4×) and `serus_darkweb_scan` 47 s (5×) as the largest tool-time consumers, consistent with the 14-day `tool_usage_log` totals (`minimax_correlate` ~875 s, `serus_darkweb_scan` ~749 s).

- **KNOWN GAP in the new telemetry — runs that die before `finish()` leave NO row.** The invocation row and the buffered step rows are written only in `finish()` (telemetry.ts comment: "a run that dies before finish() loses them"). Verified live on 2026-10-30: JD's `pattyspartyrental` thread (`06175985`) had a run start 03:18:34.19Z; its last `tool_usage_log` row is at 03:19:25.7Z (~51 s in; only 3 rows fall in the run's window), but `threads.last_heartbeat_at` is 03:20:19.2Z, **105 s** after the start — past the 90 s point where the finalize window opens, inside the 180 s budget. So the isolate stayed alive and silent of tool calls for about 54 s after its last tool, and was probably killed between 105 s and ~120 s (inference from the 15 s pulse cadence). `recovered_at` is 03:22:05.0Z (`stale heartbeat recovered by health sweep`; an earlier draft of this note said 03:22:07Z and "~51 s in, far inside the finalize window", both wrong). `orchestrator_invocations` has **no row** for it. JD's pasted run diagnostic (Interrupted / STALE_HEARTBEAT, "115 artifacts · 102 tool calls", $1.31, last stage Report) agrees with the timestamps; its 102 tool calls look thread-wide, since this run's window holds only 3 logged calls. So `unfinished_steps` / `salvage_*` can explain completed runs, **not** an isolate that is killed mid-run. `tool_usage_log` (written per call) is the only durable trail for such a run. I did not list this in #900's limitations; it belongs there. Closing it needs a design change (an up-front row plus phase breadcrumbs, which means a schema change — `finished_at` and `duration_ms` are NOT NULL), not a patch. **That design is now written up in #903.**
