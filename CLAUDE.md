## 🧭 Session hygiene — stay in this session, or start a new one? (JD, 2026-10-19)

JD asked to be told when to start a fresh session and when to stay and keep compacting.
**Claude reports one line, unprompted, at three moments:** right after a compaction, when a
PR merges, and before starting a new stage or task. The format is
`Session check: STAY — <reason>` or `Session check: START FRESH — <reason>`. When the answer
is START FRESH, the line also names where the handoff was written and gives the opening prompt.

**Start a fresh session when any of these holds:**
- A stage or PR has merged and the next one is about to begin. One session per stage or PR is
  the default boundary.
- This session has already been compacted **twice**. Each summary drops detail, so a third pass
  works from a summary of a summary. Count the summaries; do not guess. In a remote session, run
  `grep -c '"isCompactSummary":true' ~/.claude/projects/*/*.jsonl`.
- The work changes channel: frontend, edge deploy and schema each have their own recipe and traps
  (see the deploy topology below).
- The session shows drift: it re-reads files it already read, re-derives settled facts, or
  contradicts one of its own earlier measurements.
- The container was reclaimed, or the branch was reset under the session.

**Stay, compacting if needed, when any of these holds:**
- There is uncommitted or unpushed work, or a verification run is in progress.
- The session owns an open PR that is red or still waiting on CI. PR subscriptions and
  `send_later` check-ins belong to the session that created them; a new session must
  re-subscribe and re-arm them.
- The next step depends on detail that exists only in this conversation. Write that detail down
  first (PR body, plan or handoff), then decide.

**Before starting fresh, check all of these:**
- Everything is committed and pushed.
- These are written into the newest `SESSION_HANDOFF_*.md` or the open PR's body:
  - open PRs and their CI state
  - active subscriptions and pending check-ins, with their trigger ids so the old ones can be cancelled
  - JD's standing decisions made in the session
  - the exact next step
- JD has been given the opening prompt to paste into the new session.

**Rule of thumb:** staying costs little until the second compaction. After that, a fresh session
with a good handoff is more accurate than a third summary.

## ⛔ Run-termination invariants — 48 hours of incidents live here (2026-07-26)

Full write-up: `INCIDENT_2026-07-26_termination-and-ghost-recovery.md`. Two invariants
now hold the line. **Do not "simplify" either one away.** Both are pinned by tests
(`recovery_test.ts`, `orchestrator_finalize_test.ts`, `intermediate_step_plan_test.ts`)
that assert the kill switches ship ON — if you flip one, those tests fail loudly, which
is the point.

- **I-1 — a thread with no run marker is NOT an interrupted investigation.** A blank
  thread is born `status='active'` (DB column default) with `run_started_at` NULL, and
  `isStaleActiveThread` falls back to `updated_at`, so without `hasRunMarker()` the
  health sweep reaps a thread the analyst never typed into and posts a fake "Findings
  report — recovered run". This shipped for ~11 days: 14 ghosts, 192/264 threads eligible.
- **I-2 — `status='finished'` may only *present as complete* with a durable
  report-shaped assistant message or an explicit `finalize_no_findings`.** `finished` is
  written on THREE different paths (clean finalize, `onError`, stale recovery); painting
  all three green is how a 10-character `"I'll start"` stub and a real report looked
  identical. Unmet contract ⇒ `recovery_reason` ⇒ UI renders **Interrupted**.

**The termination oscillation — read before touching `toolChoice`.** This project has
twice swung between extremes and broken production both ways:
  - `FORCE_TOOL_CALL_UNTIL_FINALIZE=true` forced a tool call on EVERY intermediate step →
    removed the model's only natural exit (a text-only report) → self-completion 61%→25%.
  - Pure `"auto"` everywhere → unfinished `"I'll now run…"` narration ends the run and
    marks it COMPLETE.
  The resolution is **phase-aware, not global**: `REQUIRE_TOOL_CALL_IN_OPENING_PHASE`
  forces a tool call *only* while the run has admitted **zero** tool calls **and** the
  latest user message parses as a seed. It releases the instant work starts. Never
  "fix" a termination bug by flipping a global toggle again.

**Also settled, do not re-litigate:** intent is NOT inferred from prose. A future-intent
regex was implemented and removed — it matched the legitimate closing line *"Drop a seed
and I'll run the investigation from TRIAGE through REPORT"*, fabricating a report on top
of a plain answer. Structural signals only (report shape, phase, length floor); anything
unclassifiable falls through to the completion contract and is labelled honestly.

**`stopWhen` cannot prevent a natural stop** — it only ADDS stop conditions. The SDK's
`finishReason:"stop"` on a text-only step is not vetoable from there. Don't try again.

  in the Evidence count, and keep their `subject_unlinked_reason`. The fix removes their

  disappear is a regression, not a tightening.

## ⛔ SETTLED — do not re-litigate, do not "harden" as a drive-by

Three decisions have each been re-opened by a well-meaning audit at least once. If a future
scan flags one, the correct response is a single line — *settled, see CLAUDE.md* — not a
fresh analysis.

- **`REVEAL_BREACH_DATA` stays ON.** `env.ts` defaults it true, on purpose, on the owner's
  account, while the app is in development: the owner uses raw breach output to build and
  correct the product, and masked values make that impossible. An automated audit flagged
  the default as a critical safe-by-default violation (2026-08-10) and the recommendation
  was **rejected** — it read the default and never read the authorization comment six lines
  above it. Verifiable at `/health` (`reveal_breach_data`). *The one real thing to know for
  release:* flipping it to `false` gives **masked-by-default, not click-to-reveal** — no
  per-item reveal control exists in the UI. The release posture is a small feature build,
  not a deploy-day config change. Scope it before release day.

- **`MAX_PAID_CALLS` stays bounded.** It was set to `POSITIVE_INFINITY` during a session and
  reverted on operator instruction. An unbounded run does not finish more often — it runs
  out of wall-clock instead of budget and dies in a worse place. The cap and the
  finalization state machine have to be designed together. The right way to reduce cap
  pressure is the dispatch guard above, not a bigger number.

  because it matched the legitimate closing line *"Drop a seed and I'll run the
  investigation from TRIAGE through REPORT"* and fabricated a report on top of a plain
  answer. Structural signals only.

### ⛔ Ship in SMALL PRs — a large PR cannot be deployed or reverted here

This is not style advice; it follows from the deploy topology above.

1. **`/health` proves a BUILD, not a change.** Ship six changes in one build and a regression
   cannot be bisected — there is nothing finer-grained to look at.
2. **The behavioural-proof-key trick is per-build.** One new key (`checks.synthesis` →
   `checks.rejected_cluster_sweep` → `checks.credentials`) cannot prove six changes landed.
3. **Edge deploys are serialized and manual.** Each edge PR needs its own stamp → surgical sync →
   hard gate → Lovable message → `/health` verify → ledger cycle. Batching changes does not batch
   the risk, it concentrates it.
4. **Frontend and edge ship on different channels.** Frontend goes live on merge via Vercel; edge
   does **not** ship on merge at all. **Never mix them in one PR** — it can be neither cleanly
   deployed nor cleanly reverted.
5. **Review catches what CI cannot.** Every defect caught in review here was a *timeline or
   identity* error that passed the full suite, typecheck, lint and build. Large diffs hide exactly
   that class.
6. **The merge queue is the bottleneck.** Big PRs sit in draft; small ones merge.

Rules: one PR = one behaviour change + its tests + its kill switch · never mix frontend and edge ·
never mix a schema change with the code that depends on it (schema first, applied and verified,
*then* the code) · every behaviour-changing edge PR adds one new `/health` key or durable log event ·
at most one edge PR in flight, frontend PRs run in parallel · docs and ledger updates ride
separately · run `npm run test:e2e` by hand for anything touching `src/`.

A worked six-PR decomposition of the lineage work is in §7 of the 2026-09-13 handoff.

### A 403 is not a dead credential

The 2026-09-12 datasheet listed four "permanently dead" providers. One
