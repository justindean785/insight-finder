# `mcp` — the fourth edge function, and why its source lives here

> This directory is **not built, imported, or executed by this app.** It is the
> canonical, reviewable record of a Supabase Edge Function that Lovable deploys.

## What this is

`mcp` is a **fourth** live Deno edge function on the shared Supabase backend
(`skzqwbyvmwqarfgfvyky`), alongside `osint-agent`, `evidence-export`, and
`security-test-lab`. It exposes the analyst's investigations over the Model Context
Protocol — `echo`, `list_investigations`, `get_investigation`.

It reached production **without ever existing in this repository's history.** It was
authored inside Lovable, lives in the mirror (`seeker-spark-search-5362c57c`), and was
deployed from there. `git log --all -- supabase/functions/mcp` in this repo is empty.
That is the drift this directory exists to end.

## Provenance — the source vs. the artifact

The deployed file, `supabase/functions/mcp/index.ts` **in the mirror**, is generated
build output. Its first two lines say so:

```
// AUTO-GENERATED by @lovable.dev/mcp-js — do not edit. Regenerated by the Vite plugin.
// To take ownership, delete this banner line; the plugin then leaves the file alone.
```

The generator is `mcpPlugin()` from `@lovable.dev/mcp-js/stacks/supabase/vite`, wired
into the **mirror's** `vite.config.ts`. It bundles these files into that single Deno
entry point at build time.

So the reviewable unit is this directory, not the generated function. Editing the
generated file directly is overwritten on the next build unless the banner line is
deleted first.

## What is deliberately NOT here

By decision (2026-08-11), this repo carries the **source only** — no build wiring:

- `mcpPlugin()` is **not** added to this repo's `vite.config.ts`
- `@lovable.dev/mcp-js` is **not** added to `package.json`

Reason: this repo's Vite build is what ships Vercel production. Adding the generator
here would change that build and create a second generator racing Lovable's. Lovable
remains the only thing that generates and deploys `mcp`; this repo is where the
contract is reviewed and where changes are authored before being synced.

Consequences, both intentional:

- `src/lib/mcp` is in `tsconfig.app.json`'s `exclude` — without the
  `@lovable.dev/mcp-js` types, `npm run typecheck` cannot resolve its imports.
- `src/lib/mcp/**` is in `vitest.config.ts`'s coverage `exclude` — it is never
  executed, and the coverage ratchet floors sit within 0.2% of the measured value.

Because these files are not typechecked, `src/test/mcp-contract.test.ts` asserts their
contract **as source text**, the same way `catalog-guidance.test.ts` reads
`tool-registry.ts` and the edge suite's `reviews_wiring_test.ts` reads `index.ts`.
That test is the drift alarm. If it fails, this copy and the deployed function have
diverged, or someone changed the contract without changing the record.

## Syncing

Paths are identical on both sides, so the sync is a straight copy — keep it that way,
because a path translation is exactly where drift re-enters:

```bash
cp -R src/lib/mcp/. <mirror-clone>/src/lib/mcp/
```

Then follow the normal backend recipe in `CLAUDE.md`: review the diff, push to the
mirror, and treat the **explicit Lovable deploy** as a separate step. A mirror push
syncs code; it does not deploy.

## Open integrity issue — read before extending this

`get_investigation` returns `messages` and `artifacts` via `select("*")`, verbatim, as
`structuredContent`. That path does not pass through the frontend/report integrity
layers, so it can surface:

- quarantined rows without their authority semantics — `subject_unlinked` lives inside
  the `metadata` JSON, not in a column, so a column allowlist cannot express this; the
  DTO has to project *inside* `metadata`
- confidence and labels without the collision presentation the Evidence and Report
  surfaces apply
- breach values in a materially different form than the analyst-facing surfaces, which
  matters because production deliberately permits revealed breach data for authorized
  investigations
- raw assistant message text, including report tables and interrupted-run stubs,
  without the `recovery_reason` interpretation the UI applies

Replacing the raw rows with an explicit, authority-aware DTO is **integrity-critical
work requiring sign-off** (see the evidence-integrity rules in `CLAUDE.md`). It is not
done here. This directory only brings the contract under governance so the change can
be reviewed rather than discovered.
